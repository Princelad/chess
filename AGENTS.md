# AGENTS.md — C++ Multiplayer Chess

## Build & test commands

```sh
cmake -S . -B build          # configure (fetches SFML 3.1.0 + GoogleTest v1.17.0 if needed)
cmake --build build          # build everything
ctest --test-dir build       # run all tests
```

Single test:
```sh
ctest --test-dir build -R "MoveGen.KingCastling" --output-on-failure
```

When adding a new `.cpp` file, register it in the relevant `CMakeLists.txt`:
- `tests/CMakeLists.txt` → `add_executable(chess-tests ...)` for test files
- `core/CMakeLists.txt` → `add_library(chesscore STATIC ...)` for rules engine sources
- `client/CMakeLists.txt` → `chessclient` for GUI sources, including `src/widgets/`

## C++17 gotchas (already bitten)

- **`constexpr operator==`:** `explicit constexpr operator==` is valid; do NOT `= default` on `==`/`!=` in C++17 (no defaulted comparison operators).
- **`Piece::None()`:** use a static member function, not a static data member (incomplete-type issue at point of declaration).
- **`std::optional<Board>` dereference:** `Board::fromFen()` returns `std::optional<Board>`. Dereference with `*board` or `board->`, never `board.`.
- **`find_if_not` + inverted predicate:** `find_if_not(begin, end, isNotSpace)` finds the first *space*, not the first non-space. For trimming use `isSpace` with `find_if_not` (or `isNotSpace` with `find_if`).
- **Chat enter-send:** in `GameScreen`, `chatInput_` is focused by click; while focused, `handleEvent` forwards `KeyPressed` into `chatInput_.handleEvent` (Enter fires its `onCommit` → `sendChat()`). Escape unfocuses first. Text is typed via `TextEntered`, so backspace arrives as `TextEntered('\b')`, not a key press.
- **Keyboard play (9.6):** in `GameScreen`/`LocalGameScreen`, arrows move a board cursor (`keyCursor_`, wraps at edges, syncs from mouse presses); Enter selects own piece then commits to the cursor square; `[`/`]` step the move list (replacing the navigator's Left/Right in those screens — Analysis still uses arrows); `F` calls `BoardView::toggleFlipped()`; `?`/`Slash` toggles the help overlay (`showingHelp_`, closes first on Esc). Pure mapping lives in `client/src/keyboard.h` (`keyToAction`, `moveCursorStep`). Cursor rendering rides on `HighlightState::cursorSquare`.
- **INI config:** `Config` flattens keys as `section.key`, sees `[section]`/`key = value`, strips `#`/`;` comments, and persists to `~/.config/chess/config.ini` (created on save). Settings are applied and re-saved immediately from the Settings screen; `sound.{volume,muted}`/`animation.{enabled,duration}` are consumed by the SFX manager and move animator (9.7/9.8). Chess-clock presets live in `general.time_control` (11.1, cycled on the ConnectScreen) and join messages carry them.
- **Themes (11.6):** palettes live in `themes.h` (`BoardTheme`, persisted as `board.colors`); Wood and Moss were appended after `Dark` on purpose — persistency by name means appending preserves every previously stored value, so don't reorder the enum. Piece sets (11.6) are named dirs under `assets/pieces/` (`cburnett` default, `merida`, `chessnut`), each with a README.md credit — new licenses come from lichess-org/lila's `COPYING.md` table, the authoritative record (avoid its NC/"freeware" sets; cburnett is also listed as CC BY-SA 3.0 via Wikimedia in the project README). Config key `pieces.set` (values = dir names, unknown → `cburnett` via `pieceSetFromName`); the explicit custom `pieces.path` still ranks first in `loadPieceTextures`' dir order (custom path → `assets/pieces/<set>/` under all three relative roots → legacy flat root fallback), so the Settings cycler's status text warns when a custom path is active — cycling the named set does nothing while a path overrides it. Loader semantics unchanged: `reloadPieces()` keeps the previous 12 textures on any failure.
- **Chess clocks (11.1):** protocol is append-only v2 — `JoinMsg`/`WelcomeMsg` carry the "m+s" time-control string (empty = unlimited; `net::parseTimeControl` in messages.h refuses malformed strings to unlimited, and the server canonicalizes the payload before pairing/storage). The matchmaker pairs only equal TC strings. `server/src/clock.{h,cpp}` is a pure `MatchClock` fed injected timestamps (unit-testable without sockets): White's clock starts at `Match` construction, each accepted move charges the mover's elapsed time plus the Fischer increment, and the broadcast `ServerMoveMsg.remainingMs` (0 = unlimited) tells both clients the on-move player's fresh remaining. `Match::pollClock` runs every server-loop pass and the select wait shrinks to 100 ms whenever a clock is live, so `GameOverReason::Timeout` flags fire promptly; rated-flow treats it like any decisive result. Client side: `Hud::syncClocks` re-syncs at each `ServerMoveMsg` and the side on the move ticks locally between syncs; unlimited games show nothing.
- **Per-class ratings (11.1b):** schema rev 3 adds `player_ratings (player_id, class, rating/rating_deviation/volatility/wins/losses/draws/last_rated_at, UNIQUE(player_id, class))`; the class string is `classifyTimeControl(tcString)` verbatim ("unlimited" for empty/unparsable). Rows are sparse — never materialize defaults on registration; `classRatingFor` reads a missing class as factory 1500/350 and `applyRatedGame`'s `ON CONFLICT` upsert materializes on the first rated game in that class. The rev-2→3 migration seeds `INSERT INTO player_ratings ... SELECT id, 'unlimited', <flat columns> FROM players` verbatim (COALESCE for last_rated_at), so historical accounts own an "unlimited" row that exactly mirrors what they had. The `players` table is now the **mirror of the unlimited class**: unlimited rated games and unlimited idle growth rewrite its rating/RD/vol/counters/last_rated_at in lockstep; non-unlimited classes never touch it. This keeps the flat wire (ProfileMsg at login + post-game, WelcomeMsg opponent rating, leaderboard top-N/minGames) single-numbered with zero protocol churn — post-game `RatedUpdate` players carry the game's class figures, `applyIdleGrowth` grows every owned class row off its own `last_rated_at` and stamps the returned Player with the newest-rated class (flat login display), and the server's `opponentRow` lambda reads `classRatingFor(id, match's TC)`. Test-side gotchas: the two pre-existing idle-growth tests rewind `players.last_rated_at` — under 11.1b the idle driver is the CLASS row, so they rewind both tables; and a leftover temp db from an aborted run (user_version 1, column already ALTERed) poisons reruns — migration sim tests must `std::filesystem::remove(path)` up front. In simulating a rev-1 file for the seed, never rebuild `players` with `CREATE TABLE AS SELECT` — it strips the PRIMARY KEY and the FK-backed seed INSERT then fails with "foreign key mismatch"; recreate the table with explicit DDL. (11.1b audit hardening: `applyIdleGrowth` runs the whole pass — class-row writes plus the players mirror — inside one `Transaction`, so a crash mid-pass can no longer leave a partially-grown player.)
- **Reconnect & resume (11.2):** `Match` holds two private `Seat`s (`present` `Client*` + join-persistent name/playerId/rating snapshot/deviation + `resumeToken`); all sends go through `sendToPresent()` (absent seats receive nothing), and every observer reads seat data via `Match::seat(Color)` (`SeatView`) rather than the still-present `white()/black()` pointers — those are null whenever a seat is away. Protocol v2 append-only: client tag `Resume = 12`, server tags `ResumeState = 14`/`OpponentReconnecting = 15`/`OpponentResumed = 16`; `WelcomeMsg` grew `resumeToken` (trailing fields must be serialized AND deserialized — legacy-shaped packets fail as intended). Grace flow: solo disconnect = seat absent + `OpponentReconnectingMsg{ceil(graceSec)}` to the survivor + server-side deadline (`ServerConfig.reconnectGraceMs`, `--grace-ms` e2e knob); absent pieces still clock-run, so `pollClock` can flag during grace — wildcard `pollReconnect(nowMs)` ends the game `opponent wins / Disconnection` when the deadline lapses, and both seats absent in one pass = instant unrated `Abort`+`Disconnection`. `ResumeMsg{token}` routing lives in the `Connected`-state branch (`handleResume`): `Match::resume` rebinds the seat (or, for a finished match kept in retention for exactly the grace window, returns `ReboundOver` and the server replays ResumeState + `GameOverMsg` + fresh `ProfileMsg`; server.cpp erases matches only past `retentionEnded`). `endGame()` notifies present seats, runs the gameOver callback while seats are still attached (rated/archive hook uses seat snapshots, so results rate even after someone left), and only then detaches clients — reorder that and profile re-sends break. Client: GameScreen owns `resumeToken_` (from WelcomeMsg via ConnectScreen); a mid-game drop arms a Backoff→Connecting→AwaitingResume loop (1 s retries, ~30 s window, instant give-up on an `ErrorMsg` while waiting) and `applyResume()` rebuilds the screen in place by replaying the SAN chain (`hud_.setGame`) with `Hud::syncClocks(whiteMs, blackMs, sideToMove)` — everything after `switchScreen` must `return` immediately, so the rebuild never switches screens. Never touch a seat's stale `Client*` after erase: presence, not the erased object, is the truth.
- **Opening names (11.5):** pure `client/src/eco.h` — `ecoLookup(sans)` prefix-matches a **compiled-in** ECO table (no assets/IO) by **longest-prefix-wins** over the SAN history; unknown first moves (junk, `h3`, `Na3`…) return nullopt and the HUD shows nothing, but a listed prefix labels the game **for its whole life** — a listed move-1 umbrella catches every continuation afterward, so there is no "label disappears on deviation" behavior; don't add expect-nullopt tests for deep junk after a listed prefix. Suffix normalization: `ecoToken` strips `+` `#` `!` `?` from BOTH sides (the table even carries a literal `Bb4+` token), so check-diverted lines still match. Both HUD SAN-mutation points (`Hud::setGame`/`appendMove`) re-run `refreshOpening()` — `setStatus` is never used (timed channel); display is a right-aligned label on the "Moves" header row. The table must stay code-conservative (11.5 audit correction): the working invariant is not a hard ply depth but code unambiguity per spelling — the table carries full main-line ECO spellings that legitimately run to 10 plies (Najdorf/Dragon/Classical/Scheveningen); what stays forbidden is stamping an ambiguous prefix with a code. Remember there is NO bare `1.d4 d5 c4 e6`→London/Bf4 entry — umbrella entries like "d4" (A40) anchor every continuation of that first move.
- **Takeback (11.3):** classic two-ply frame — a request is legal only when the asker is on the move with ≥2 plies and the opponent is seated; acceptance retracts the asker's last ply plus the opponent's reply, so the asker is again on the move in the prior position. The server rolls back by truncating `Match::sanHistory_` by 2 and re-chaining `san::fromSan` from the start position — the same reconstruction as a token resume; `Board::undoMove` is NOT used (it restores movegen-internal state, not match-level scope). Protocol append-only: client `TakebackRequest = 13`/`TakebackAccept = 14`/`TakebackDecline = 15`, server `ServerTakebackRequest = 17`/`TakebackAccepted = 18` (carries the full remaining SAN list guarded by `MaxResumeMoves = 512`)/`ServerTakebackDecline = 19`. Lifecycle: one pending per match (`takebackPending_` = asker seat index), dissolved by the next accepted move, a decline (the asker's own decline doubles as a self-cancel — its notice always lands on the asker's seat), a disconnect (either seat), or `endGame`; a request while the opponent is mid-grace fails fast (`ErrorMsg` "The opponent is away"), never queues. Bots auto-accept inside `Match::handleTakebackRequest` (no round trip; safe because a bot never thinks while the asker is on move). Clocks are NOT refunded — after the two `completedMove` charges, `MatchClock.onMove` already equals the post-rollback `sideToMove`, so the rebuilt turn just keeps running; no clock surgery anywhere. Client: GameScreen holds `takebackOfferPending_` (opponent's prompt shares the draw offer's accept/decline buttons; draw wins visibility while both pending); `applyTakeback(vec<string>)` rebuilds via `hud_.setGame` + `goEnd` (11.2's `applyResume` got the same `goEnd` — it used to sit at ply 0 until the first click), calls `anim_.cancel()` (new `MoveAnimator` API) and drops stale selection/drag/promo state. History-append rule unchanged: rollbacks replay via `setGame`, never `appendMove`. (11.3 audit hardening: `applyTakeback` replays the truncated chain into scratch locals first and only commits `sanHistory_`/`board_`/`takebackPending_` once the whole replay applies — the original form truncated state before validating, so an "unreachable" mid-chain failure would have desynced the match silently with no `TakebackAcceptedMsg`.)
- **Login rate limiting (R2):** per-connection throttle in `handleLogin` — `Client::failedLogins`/`Client::loginLockedUntil` (steady clock). A lock REFUSES the attempt outright ("Too many failed logins — try again in N seconds") and does not count it; counting failures are wrong passwords and rejected registrations (the "account is password protected" hint deliberately does NOT count — empty-password probes carry no attack surface and must stay responsive). The lock arms from the SECOND consecutive failure (`1s << (n-2)` capped at 60 s) so a single typo + immediate correct retry is never delayed — that property is asserted by `RatedE2eTest.WrongPasswordIsAnErrorAndRetryRegistersLogically` (no sleep) alongside the throttle test; connection lifetime scope means a reconnect sidesteps it (accepted: the point is slowing an in-session brute force, not identity hardening). Success resets both fields. The throttle message never reveals the account's existence either way. (11.9 audit fix: the backoff exponent is clamped to 6 before shifting — the failure count is unbounded and a patient attacker can reach shift widths past `int` otherwise; 1000<<6 = 64 s already saturates into the 60 s cap, so behavior past six failures is unchanged.)
- **Rematch (11.7):** post-game continuation on the SAME connection — no rejoin, no queue. Protocol v2 append-only: client `RematchRequest = 16`/`RematchAccept = 17`/`RematchDecline = 18`, server `ServerRematchRequest = 20`/`ServerRematchDecline = 21` (decline carries `withdrawn` 0/1 via `writeFlag`; the asker's own decline message doubles as a self-cancel → `withdrawn=true`); there is NO `RematchAccepted` server tag — the fresh `WelcomeMsg` of the rebuilt match is the acceptance signal for both seats. Backbone: `endGame` no longer detaches — seats stay attached with new `ClientState::GameOver` for exactly the match's retention window (= reconnect grace), so the rematch trio routes through `client.match->handleMessage` in the shared `InMatch||GameOver` switch case, and `Match::handleMessage` pre-routes all three rematch handlers before its `!active_ → "Game is over"` gate (they self-check: `active_` → "Game not over yet"; `retentionLapsed()` (stale frame, sweep not yet run) → "No game to rematch — session expired"; opponent absent → "The opponent is away"). Accept fires the `rematchCallback_` (set via `setRematchCallback` in `startMatch`; the two lambdas `onRematch`/`startMatch` are mutually recursive so `startMatch` is held as `std::function`): both seats must be present, `detachAllSeats()` clears the old match, and the same two clients re-pair with colors swapped (`startMatch(*black, *white)`), fresh resume tokens, same TC string and rated flag; a rematched bot restarts `startBot` against its swapped color (the server knows which seat is the bot from the old seats). Lifecycle: one pending per match (`rematchPending_` = asker seat index), dissolved by a decline/self-cancel, either seat's departure (`leave` for voluntary, `handleDisconnect`'s `!active_` branch for drops — no notices when nothing pending, decline notice with `withdrawn` otherwise), or the retention sweep. IMPORTANT server-loop detail: the retention sweep + bot cleanup moved BEFORE the `selector.wait` (an idle server never got them — finished matches aged out only on event-driven passes, another latent bug). Also: `ClientState::GameOver` bots may NOT be erased by the bot sweeper while their match is still retained (condition: `state != InMatch && !(state == GameOver && match != nullptr)`), and the join handler must NOT `push_back` a bot mid-client-loop — the push reallocates the vector and invalidates the loop's own iterator (latent use-after-free my bot-rematch e2e exposed); bots spawn post-loop from `botSpawnQueue` instead. Client: `GameOverScreen` pumps the connection inside `update()` (it used to not poll at all) and owns the rematch conversation — Rematch button (enabled only live), Accept/Decline row when `ServerRematchRequest` arrives (Accept focused, both disable on answer send until the WelcomeMsg), `ErrorMsg` clears any local state into the status line, and the rematch `WelcomeMsg` constructs a fresh `GameScreen` exactly like the connect flow (color/rated/TC/token all from the message). Note: late token-ghost rejoins of a finished match (`ReboundOver`) stay in `Connected` and cannot rematch — only seats that were present at game-over can.
- **Chat polish (11.8):** client-local only, zero protocol surface. Pure `client/src/chat_log.h` holds the data + helpers: `ChatEntry{name, text, epochSec}` (empty name = system line; own echo uses `YouName()`), `chatTimestamp` (local "HH:MM" via `strftime`; the chat test pins `TZ=UTC` because localtime is process-global), `chatNameColor` (FNV-1a over name bytes → index into a light palette, readable on the dark panel; own line renders fixed gold instead) and the mute persistence (`chat.muted` key, CSV of exact names, blank segments skipped, verbatim matching — the writer only ever emits names it stored, so stray spaces in a hand-edited config are their own name). `GameScreen` owns all wiring: `addChatLine`/`addSystemChat` centralize the 50-line cap (every `chatLog_` push goes through them — nothing pushes directly anymore); `sendChat` intercepts `/mute <name>` + `/unmute <name>` (name = rest of line, spaced names allowed; feedback as system lines; unknown → usage line) and only sends non-command text; incoming `ServerChatMsg` re-checks `chatMutedFromConfig(app_.config())` per message so a mid-game mute applies instantly; `drawChat` renders three `sf::Text` per line (dim `[HH:MM]`, colored `name:`, gray text) with the old ~6 px/char truncation estimator reapplied to each part's remaining width. The mute check never contacts the server and the opponent's client is unaffected (their offer/message still relays server-side; only this client's log suppresses it). (11.8 audit hardening: `chatMuteNamePersistable` gates the mute command — a name containing `#`/`;`/`=`, control characters or edge whitespace would round-trip through the INI store modified by `Config::load`'s trim/comment rules and mute a different string after a restart; the command answers "That name can't be muted safely" instead.)
- **Leaderboard (10.4):** `PlayerStore::topPlayers(limit, minGames = 1)` ranks accounts rating-DESC / name-ASC, only those with ≥1 finished rated game. Wire: `LeaderboardRequestMsg{limit}` → `LeaderboardListMsg{players}` (protocol v2, append-only tags; `MaxLeaderboardEntries = 100` guard on deserialize). The server answers in every connection state beside the archive handlers (server clamp 100 == wire guard; without `--db` it replies `ErrorMsg` "This server has no leaderboard"). Client: `LeaderboardScreen` (read-only list panel, "(you)" own-row highlight) entered via the ConnectScreen "Leaderboard" button; the connect flow's `archiveBrowse_` became `BrowseTarget {None, Archive, Leaderboard}` sharing the renamed `ConnectingBrowse` phase. Drive-by: the archive server clamp was also aligned from 200 to 100 so replies can never exceed the `ArchiveListMsg` wire guard.
- **Game archive (10.3):** the server answers `ArchiveRequestMsg{limit, mineOnly}` / `ArchiveGetMsg{id}` in any connection state with `ArchiveListMsg` / `ArchiveGameMsg` (or `ErrorMsg`); `mineOnly` for guests degrades to the global list. `Match::sanHistory_` feeds the row insert in the game-over hook — only games with ≥1 move are archived (`Abort` games with zero moves aren't). Replay rebuilds moves by chaining `san::fromSan` over the record's SAN list (honouring `startFen`); PGN export lives in pure `client/src/archive_pgn.h` (`gameToPgn`), copy via `sf::Clipboard`. Entry points: ConnectScreen side button (connects without queueing; with a password it logs in first, `ConnectingArchive` phase) and GameOverScreen button (pushed so Esc returns; disabled without a live connection).
- **Move history records ONCE:** the online server echoes your own move back via `MOVE`, so `GameScreen` must NOT append a local move — the echo during `update()` is the single append point via `Hud`/`MoveNavigator::appendMove`. `LocalGameScreen` (no server echo) records its own moves.
- **runServer's flag is a SHUTDOWN flag (7.1-audit fix):** the loop is `while (!shutdownFlag.load())` and `stopServer` stores `true`; the e2e harness feeds runServer its own false-initialized atom, so every e2e passes even when the real `main.cpp` wiring is wrong — 7.1's rename regressions hid for months because main.cpp still initialized a `running{true}` atom from the phase-4 idiom and passed it in, making the standalone binary bind the port and exit within milliseconds ("Listening…" then "Shutting down" in the same second). When touching server lifecycle code, keep main.cpp's atomic named `shutdownFlag`/initialized `false` and remember the harness can never catch this class of bug — only launching the actual binary can.
- **Accounts & ratings (10.2):** protocol is **v2**. `LoginMsg{name, password}` (unknown name + non-empty password = transparent auto-register; empty password = guest, joins via plain `JoinMsg` as before) gets a `ProfileMsg{name, rating, deviation, isGuest}` reply — also re-sent after rated updates. `WelcomeMsg` carries `{rating, deviation, rated}` (opponent's). Booleans on the wire travel as validated 0/1 bytes (`writeFlag`/`readFlag` in protocol.cpp). Rated updates happen in `PlayerStore::applyRatedGame` (one transaction over both rows + W/L/D counters, pre-period Glicko-2 inputs), wired via `Match::setGameOverCallback` in `runServer` (v1.3.1 audit follow-up); only `WhiteWins/BlackWins/Draw` rate — aborts (both disconnects) and guests/bots are never rated, while a single disconnect mid-game loses and still rates. Guest `JoinMsg` names are rejected when they collide with an account (NOCASE) — password-gated accounts must not be spoofable in chat/archive (`RatedE2eTest.GuestJoinCannotTakeAnAccountName`); logged-in clients skip the check since `playerId` bypasses the payload name. `ConnectScreen` phase `AwaitingProfile` keeps a failed login's socket alive for retries; `App::profile()` holds the latest `ProfileMsg` and `App::setLastConnection` persists `general.last_host/port/name` (never the password). `TextField::setMasked` renders '*' for the password field. Idle-period RD growth (10.2 follow-up): `handleLogin` runs `PlayerStore::applyIdleGrowth(id, now)` before `ProfileMsg` — one Glicko-2 no-game period per full idle day since `players.last_rated_at` (schema rev 2, `ALTER`-migrated from rev 1), capped at 5000 periods/RD 350; never-rated rows no-op. Rating classes are taxonomized in `db/rating_class.h` (`classifyTimeControl`, "unlimited" until 11.1 clocks give games a TC).
- **Premoves (11.4):** online `GameScreen` only. When `!myTurn_`, a committed drag/click/Enter move becomes a `Premove{fromFile/Rank, toFile/Rank}` (single slot in `GameScreen::premove_`, latest replaces) instead of a send; `trySendMove` is the queue entrance, so keyboard-arrow premoves work too. Flush is exactly one point: the `ServerMoveMsg` handler calls `flushPremove()` right after `myTurn_ = true` — the echo remains the single history-append point (a flushed premove must never also `appendMove` locally). Resolution is pure `client/src/premove.h` `resolvePremove(board, premove)`: the legal move matching from/to at flush time; capture-frames onto empty squares, own-piece landings and pin breaks drop with "Premove illegal"; king-by-two resolves to the castle; promotion frames send the queen move directly (no picker can exist for a hypothetical position). Ghost rendering is `BoardView::drawGhostPiece` (110-alpha piece at the landing square) + `HighlightState::premoveFrom/premoveTo` tints, drawn only when `!myTurn_ && navigator().atEnd()`. Cancel = right-click/Esc/Space (`Deselect`); cleared on `GameOverMsg`, `applyTakeback`, and `applyResume`. No protocol changes — a flushed premove is a plain `MoveMsg`.
- **Move animation (9.7):** pieces slide via `MoveAnimator` (in `client/src/move_animator.h`, header-only) — capture the pre-move state, advance `update(dt)` on the fixed-timestep, read eased `progress()` in `draw()` (frame-independent). Triggers are exactly the append points: the online `ServerMoveMsg` handler and `LocalGameScreen::applyMove`/`applyEngineMove`. `BoardView::drawPieces` takes a `const MoveAnimator*` (Analysis passes `nullptr`) and skips destination squares while animating. Duration/enable come from config keys `animation.enabled`/`animation.duration` (0/false = instant snap); no animation while replay-stepping. On the deciding move, the game-over screen switch is delayed via `GameOverTransition` (`client/src/game_over_transition.h`) so the final animation and mate/capture sound play out (`gameOverDelaySec` floors all delays at 0.55s).
- **Sound (9.8):** `client/src/sfx.h` ships `SoundManager` (App-owned, `app_.sounds()`) with procedurally synthesized 16-bit/44.1 kHz clips (no asset files) — move bump, capture thock, two-tone check, descending mate. Pure `classifyMove(before, move)` picks the clip with precedence Checkmate > Check > Capture (incl. en passant) > Move, and is fired at the same append points as 7 animation. Requires the SFML `Audio` component — root `CMakeLists.txt` requests it (`SFML::Audio`/`sfml-audio`), and the FetchContent fallback builds audio too (needs OpenAL on Linux). SFML 3.1 nuances: `sf::Sound` has no default ctor (initialize with a buffer), `SoundBuffer::loadFromSamples` takes a 5th channel-map arg (use `{sf::SoundChannel::Mono}`), samples are `std::int16_t`.
- **Board input is press→release:** left press starts a `DragTracker` + selects own piece; the move is committed on release (drag-resolution or click-target). Left press clears arrows/circles; right press deselects, right drag draws arrows, right tap toggles circles. Annotations live in `BoardAnnotations` (per-square, `BoardView`-rendered) and are cleared when the board leaves the live position.
- **Auto-queen defaults ON** (config key `general.auto_queen`, toggled via the picker's `Checkbox` and the Settings screen); when enabled a promotion commits the Queen move directly and skips the picker.
- **Chess960 castling (12.1-core):** all four fixed-square castle assumptions died; survived pieces:
  - **`State` grew `castlingRooksFrom[4]`** (indexed by `castlingRightIndex(right)` = bit order WKs, WQs, BKs, BQs; defaults h1/a1/h8/a8). FRC castling legality/execution is driven entirely by that array plus the FRC destination convention (king always ends g/c-file, rook f/d-file). `makeMove`'s castle branch must run clear(rookFrom) → clear(kingFrom) → set(to) → set(rookTo) in that order — king origin f1 can BE the rook's destination, king dest g1 can BE the rook's origin, and the king-at-g1 castle is a legal `Move{from == to, Castle}`; any set/clear ordering that assumes disjoint squares self-destructs on those overlaps.
  - **Rights clearing is color-attributed** (`makeMove`: mover color owns its two array indices for rook-lift; capture clears the CAPTURED side's two). The old hardcoded a1/h1 checks were unreachable-wrong there; a black rook squatting on h1 via a crafted FEN no longer nukes White's right. Test fixtures that replay a capture "backwards" (wrong sideToMove) must `setSideToMove` first — `MakeMove.CaptureOnA1RevokesWhiteQueenSide` attrition proves it.
  - **Castle legality attacks check the king hop (origin excluded, destination included) on a board LIFTED of both castling king AND rook** (Stockfish scheme); through-king attacks always coincide with `inCheck`, which is checked first, so standard perft is unaffected — Grant's Chess960 perft suite (chessprogramming.org/Chess960_Perft_Results, pinned in `tests/core/chess960_test.cpp`) covers the exotic empties (paths are subsumed by king-hop ∪ rook-hop; "strictly between" needs no extra segment).
  - **X-FEN castling field** (`fen.cpp`): input accepts KQkq plus file letters `A..H`/`a..h`; letters grant king-side iff file > king file (else queen-side), inferred outermost rook by scanning corner→king; when there is no king/rook to infer from, the right STILL grants keyed to the traditional corner (regression-critical: `Fen.BlackToMoveLimitedCastlingEmptyBoard`'s rook-less `Qq` empty board must parse). Serializer is canonical: K,Q,k,q slot order, so input order ≠ output order (`qg` reads back as `gq`); corner-file rooks emit the traditional letter, inner rooks emit the file letter (black letters lowercased — first pass emitted `GEGe`, colliding white/black rights into the same `seen` bucket and failing 25% of generated SP FENs). Beware the char-class trap: `'K' > 'H'` — a castling char is classified BY CASE per branch, never by the `A..H` range (early version made `KQkq` white letters grant BLACK rights; `Kk` "looked duplicate" and rejected).
  - **SAN**: `toSan` is unchanged (FRC castles always end g/c-file, so `destFile == 6 → "O-O"` holds for all 960 positions); `fromSan` resolves `O-O`/`O-O-O` (and `0-0` spellings) by matching ANY legal castle landing on the wing's file, and the plain-SAN matcher EXCLUDES castle-flagged moves so `Kf1→g1` walk and the `f1→g1` castle are distinct SANs (`Kg1` = walk, `O-O` = castle).
  - **Generator**: `core/src/chess960.cpp` uses Scharnagl's direct derivation verbatim (light bishop first: `1+2*(n%4)`, then dark `2*((n/4)%4)`, queen `kthFree(n%6)`, knight pairs table over the 5 freed files, R-K-R fill left-to-right — the k-R fill loop must handle the three leftover files in FILE ORDER, first→rook, middle→king, last→rook). SP# 518 ≡ `fromStartPos()` is pinned by test; all 960 must parse→round-trip→perft-green.
- **Chess960 protocol & server (12.1-PR2):** variant string is exactly `"chess960"` (constexpr `Chess960Variant` in `messages.h`); `sanitizeVariant()` in protocol.cpp is **exact-match only** — casing/alias/unknown tags degrade to the standard game, never trust the payload. Append-only v2: `JoinMsg` grew `variant` (trailing, after timeControl) and `WelcomeMsg` grew `variant` + `startFen` (after resumeToken) — trailing fields must serialize AND deserialize (pre-12.1 packets fail as intended, asserted in `ProtocolGarbage.*LegacyShape*`). The server rolls the SP (`chess960RandomId()` → `chess960StartFen`) inside `startMatch` at PAIRING, so both seats see one identical FEN, rematches re-roll a fresh SP (variant kept), and `Match` gained a trailing `startFen` ctor param (`startBoardFrom` helper with LOG_ERROR fallback to the standard board). **The takeback rollback (`match.cpp` handleTakebackAccept) must re-chain from `startBoardFrom(startFen_)`, not `fromStartPos()`** — the matched two-ply retraction silently desyncs a Chess960 match otherwise (pinned by `Chess960MatchTest.TakebackRollbackRechainsFromFrcStart`). Matchmaker pairs only on `(timeControl, variant)` equality (standard and Chess960 never cross); bots mirror the human's variant via the now-`pair<string,string>` `botSpawnQueue`; rating classes stay TC-keyed (no variant split) and the archive row carries `startFen` (empty = standard start) so replay/PGN rebuild from the SP. **Test gotchas:** a positional argument of literal `0` binding to a new trailing `const std::string&` ctor param compiles via the null-pointer-constant rule (`std::string(nullptr)` throws — `bot_match_test` built its Match as `{}, 0`; got the 4th string param); and e2e joins must ALL be sent before awaiting a welcome (`joinVariant` in `harness.h` awaits inline — a send-then-await-then-send order stalls the second join for the whole await timeout and the pair never forms within the window).

## 0x88 board reference

- Square encoding: `squareOf(file, rank) = rank * 16 + file`
- `offBoard(sq)`: `sq & 0x88` is nonzero
- Knight offsets: `{+33, +18, +14, +31, -14, -31, -18, -33}` (rank\*16 + file delta)
- King offsets: `{1, 17, 16, 15, -1, -17, -16, -15}`
- Rook directions: `{16, -16, 1, -1}`
- Bishop directions: `{17, 15, -15, -17}`
- FEN rank parsing: `rankIndex=0` is rank 8 (top of FEN string); each rank must sum to 8 squares.
